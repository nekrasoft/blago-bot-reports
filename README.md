# bot-reports

Бот для отчётов водителя мусоровоза. Один launcher запускает Telegram- или
MAX-версию. Основные сценарии: отчёт о вывозе контейнеров, заявка на
опустошение бункеров, учёт ходок с путевыми листами. В MAX дополнительно есть
учёт рабочего времени водителя.

Этот README предназначен в первую очередь для агентов, которые впервые
открывают проект. Перед изменениями также обязательно прочитать
[`AGENTS.md`](AGENTS.md).

## Быстрый контекст

- Точка входа: [`run.py`](run.py). Переменная `BOT_PLATFORM` выбирает
  `telegram` (по умолчанию) или `max`.
- Telegram: [`bot.py`](bot.py), диалоги вынесены в
  [`bunker_report.py`](bunker_report.py) и [`trip_report.py`](trip_report.py).
- MAX: [`max_bot.py`](max_bot.py). Здесь продублированы платформенные версии
  диалогов и добавлена команда `/v`.
- API карты: [`map_client.py`](map_client.py). Источник бункеров и контрагентов,
  а также запись изменения заполненности и даты вывоза.
- Google Sheets: [`sheets_client.py`](sheets_client.py). Касса и источник
  работ для биллинга. Подтверждённые вывозы сначала сохраняются через API карты;
  [`pickup_delivery.py`](pickup_delivery.py) доставляет их в Sheets из очереди.
- MySQL: [`waybill_files_db.py`](waybill_files_db.py) и
  [`driver_work_time_db.py`](driver_work_time_db.py). Файлы путевых листов и
  рабочее время.
- [`parser.py`](parser.py) содержит OpenAI-парсер текстовых сообщений, но
  текущие точки входа его не вызывают. Не считайте его частью активного
  runtime без отдельного подключения.

## Активные команды

| Команда | Telegram | MAX | Назначение |
| --- | --- | --- | --- |
| `/bunker`, `/b` | да | да | Вывоз контейнеров: выбрать бункеры со `fillLevel == 100` |
| `/zayavka`, `/z` | да | да | Заявка на опустошение: выбрать бункеры со `fillLevel < 100` |
| `/h` | да | да | Ходки: площадка, количество, объём, до 10 фото, путевой лист и подтверждение |
| `/m` | да | да | Расход: структура, категория, сумма, обязательное пояснение и подтверждение |
| `/v` | нет | да | Рабочее время водителя за текущий день |
| `/vv` | нет | да | Суммарное рабочее время текущего водителя за прошлый месяц |
| `/vvv` | нет | да | Суммарное рабочее время текущего водителя за текущий месяц |
| `/cancel` | в диалоге `/h` | текстом в активном диалоге | Отмена |

В комментариях к старому коду встречается `/report`, но handler для этой
команды сейчас не зарегистрирован.

## Основные потоки

### Вывоз контейнеров: `/bunker`

1. Бот получает бункеры через `GET /api/bunkers`.
2. В списке остаются только бункеры со `fillLevel == 100`.
3. Выбор бункеров и редактирование отчёта не обнуляют карту. Водитель
   задаёт коэффициенты, уборку и вложения, затем видит сводку и подтверждает.
4. `pickup_submission.py` сохраняет вложения и отправляет отчёт с постоянным
   `submission_key` в API карты. API фиксирует вывоз, исполнение заявок и
   обновление бункеров; повторная отправка того же отчёта не создаёт новый вывоз.
5. `pickup_delivery.py`, запущенный из `run.py`, доставляет строку в кассу
   Google Sheets. При сбое запись повторяется; маркер `[ВЫВОЗ:...]` позволяет
   распознать уже записанную строку после неоднозначного ответа Google.
6. Коэффициенты суммируются в колонке `Объект`, номера — в примечании.
   `tbank-service` затем синхронизирует кассу в работы для выставления счетов.

Не запускайте второй экземпляр бота для диагностики production. Черновики
Telegram и MAX хранятся в `data/private-state/` и содержат данные пользователей
и вложения: каталог нельзя публиковать или добавлять в Git. Очередь доставки общая для `/b` и `/h`.

### Заявка на опустошение: `/zayavka`

1. Бот получает бункеры через `GET /api/bunkers`.
2. В списке остаются только бункеры со `fillLevel < 100`.
3. При каждом выборе бот сразу вызывает
   `POST /api/bunkers/{id}/mark-filled`.
4. В Google Sheets заявка не записывается.

### Ходки: `/h`

1. Контрагенты загружаются через `GET /api/counterparties`; доступны записи
   с `operation_type=trip_removal`.
2. Водитель выбирает известную площадку контрагента либо вводит адрес или район одной строкой.
   Район определяет доступ мастеров к отчёту и его файлам.
3. Вводится число ходок и объём. Кнопки кузова `30 м3` / `36 м3` умножают
   объём на число ходок; ручной ввод — уже общий объём.
4. Для `Частник` вводится полученная наличка. Для остальных можно приложить
   фото/PDF путевого листа либо пропустить его.
5. Прикладывается до 10 фото кузова общим набором (например, до и после),
   в том числе несколько фото одним сообщением. Фото необязательны.
6. Водитель проверяет сводку и подтверждает. До подтверждения вывоз не сохраняется.
7. API карты сохраняет отчёт типа `trip`, вложения и строку доставки в одной
   транзакции. У ходки нет позиций бункеров: она не меняет их заполненность
   и не исполняет заявки на бункеры.
8. Доставку в кассу выполняет тот же `pickup_delivery.py`, что и для `/b`.
   Постоянный `submission_key` и маркер строки предотвращают повторный вывоз
   и повторную запись при потере ответа. Черновики сохраняются между перезапусками.
9. Ходка появляется в «Отчётах о вывозе» админки и кабинета контрагента.
   Фото и путевой лист также сохраняются в `works_files`, токены идут в
   примечание кассы и далее используются `tbank-service` для писем и Bitrix24.

Для наличных сохраняются `Приход` и исключение формулы `Выручка`, как раньше.
Лимит одного файла задаётся `WAYBILL_MAX_FILE_SIZE_BYTES` (по умолчанию 10 МБ).

### Расход: `/m`

Сценарий доступен в Telegram и MAX:

Структура всегда `ЮЛ - Контейнеры` (КСП 1202), выбирать её не нужно.

1. Выбор категории: «Ремонт а/м и ТО» (182), «Хозяйственные расходы» (117)
   или «Утилизация (полигон)» (185).
2. Положительная сумма в рублях, до двух знаков после запятой/точки.
   Допускается запись `4 000,50`; нулевые/отрицательные суммы отклоняются.
3. Обязательное пояснение, до 500 символов: например `б/у колесо`.
4. Проверка сводки и подтверждение. `/cancel` или кнопка отменяет черновик.

В кассу записываются дата (Europe/Moscow), структура/КСП, операция/КСЗ,
примечание и числовой `Расход`. Контрагент, приход, объект и выручка пустые;
формула выручки не копируется. Формулы месяца и сальдо переносятся, если они
есть в предыдущих строках. Например: `ЮЛ - Контейнеры / 1202 / Ремонт а/м и ТО /
182 / б/у колесо / Расход 4000`.

`expense_outbox.py` сохраняет подтверждённый расход с UUID и автором в
`data/private-state/expenses.sqlite3` (600, каталог 700). Индекс
`idx_expenses_due(status, next_attempt_at, id)` покрывает выборку очереди,
уникальный `submission_key` — проверку повторов. Общий worker `run.py`
доставляет строку в Sheets с маркером `[РАСХОД:...]`. Потеря ответа Google
не должна создавать повторную строку. Если карта недоступна, доставка
расходов всё равно обрабатывается. Запускайте через `run.py`, иначе worker
не стартует. SQLite очереди нужно сохранять при обновлении и резервировать.

`ALLOWED_CHAT_IDS` проверяется на каждом шаге `/m`, включая подтверждение.
Если список заполнен, расходы доступны только в этих чатах, в том числе
запрещены личные чаты вне списка. Пустой список сохраняет принятую в боте
политику доступа без ограничений. Не публикуйте бота с пустым whitelist.

Команда записывает расход в кассу, не создаёт вывоз или счёт клиенту.
Текущий импорт `tbank-service` выбирает операции поступления, поэтому эти
строки не становятся работами для выставления счёта.

### Рабочее время: `/v`

Сценарий доступен только в MAX. Бот сохраняет начало, окончание и длительность
работы в таблицу MySQL `driver_work_time`. Для одного пользователя допускается
одна запись за день; повторная команда `/v` запускает подтверждение замены.
Для начала работы предлагаются кнопки `08:30`, `09:00`, `09:30`. Для окончания
работы бот предлагает три времени с шагом 10 минут; последнее округляется вниз
от времени вызова `/v`. Для учёта рабочего времени явно используется часовой
пояс `Europe/Moscow`, независимо от timezone сервера. Ручной ввод остаётся
доступен. Итоговое сообщение заканчивается `user_id` водителя в скобках, чтобы
его можно было найти поиском в чате.

Команды `/vv` и `/vvv` показывают суммарное время текущего водителя за прошлый
и текущий календарные месяцы соответственно. Ответ также заканчивается ID
водителя в скобках и содержит однозначное обозначение месяца в формате
`MM.YYYY`, например:
`За прошлый месяц (05.2026): 168 ч 30 мин. (user_id: 123456)`.

### Отчёт о вывозе бункеров: `/b`

Водитель выбирает один или несколько бункеров одного контрагента и площадки,
указывает для каждого количество к оплате `1`, `1,5` или `2`, результат уборки,
прикладывает до 10 фото и до 5 подписанных талонов. Обязательность талона
задаётся у контрагента; его отсутствие не блокирует вывоз и сохраняется как
предупреждение с причиной. Сумма коэффициентов записывается в колонку `Объект`.
Фото площадки и талоны сохраняются в `works_files`, а их токены добавляются
в примечание Sheets как `[ПЛ:wb_...]`. После синхронизации `tbank-service`
отправляет их вместе в письме с файлами работ и прикрепляет к задаче Bitrix24.
Это относится к новым отчётам после обновления бота.

## Интеграции и конфигурация

Скопируйте [`.env.example`](.env.example) в `.env` и задайте нужные значения.
Секреты и credentials не коммитить.

| Переменная | Для чего нужна |
| --- | --- |
| `BOT_PLATFORM` | `telegram` или `max` |
| `TELEGRAM_BOT_TOKEN` | token Telegram-бота |
| `MAX_BOT_TOKEN` | token MAX-бота |
| `ALLOWED_CHAT_IDS` | whitelist ID групп через запятую; пустое значение снимает ограничение |

| `MAP_BOT_API_KEY` | ключ записи в API карты |
| `MAP_BOT_READ_API_KEY` | отдельный ключ чтения; если пусто, используется `MAP_BOT_API_KEY` |
| `GOOGLE_SHEET_URL` | URL Google-таблицы, желательно вместе с `gid` листа |
| `GOOGLE_CREDENTIALS_PATH` | JSON сервисного аккаунта Google |
| `MYSQL_HOST`, `MYSQL_PORT` | адрес MySQL |
| `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE` | подключение к MySQL |
| `WAYBILL_MAX_FILE_SIZE_BYTES` | максимальный размер путевого листа |
| `PICKUP_FILE_MAX_SIZE_BYTES` | максимальный размер одного фото или талона вывоза |
| `SQL_ECHO` | SQLAlchemy logging при `1`, `true` или `yes` |
| `OPENAI_API_KEY`, `OPENAI_MODEL` | нужны только для не подключённого сейчас `parser.py` |

JSON сервисного аккаунта Google по умолчанию ожидается по пути
`credentials/google_service_account.json`. Каталог `credentials/` и файл
`.env` исключены из Git.

## Данные и схема

| Файл | Назначение |
| --- | --- |
| [`config/schema.json`](config/schema.json) | Колонки Sheets, переносимые формулы, fallback URL таблицы |
| [`data/operations.json`](data/operations.json) | Реквизиты операций; активно используется для ходок и OpenAI-парсера |
| [`data/counterparties.json`](data/counterparties.json) | Справочник для OpenAI-парсера, не для интерактивных команд |
| [`data/parsing_rules.md`](data/parsing_rules.md) | Документация правил OpenAI-парсера |

Интерактивная команда `/h` берёт контрагентов из API карты, а не из
`data/counterparties.json`.

`sheets_client.append_rows()` ищет последнюю заполненную строку по колонке
`Дата`, переносит формулы из предыдущих строк и обновляет только необходимые
диапазоны. При изменении колонок синхронно проверяйте `google_sheet_columns`,
`fill_columns` и `formula_columns`.

### Таблицы MySQL

- `works_files` должна существовать до запуска. Код не создаёт её миграцией.
  Для ожидаемой семантики upsert проверьте unique index по `file_token`.
- `driver_work_time` создаётся через SQLAlchemy при первом обращении.
  Unique constraint `uq_driver_work_time_source_user_date` покрывает условия
  чтения, upsert и месячной агрегации: `source`, `source_user_id`, `work_date`.

При любых изменениях SQL или условий `WHERE` обязательно проверяйте индексы.

## Запуск

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python run.py
```

Для прямой диагностики можно запускать `python bot.py` или `python max_bot.py`,
но штатная точка входа — `python run.py`.

## Служба и журналы

На проверенном сервере 16.10.2026 `bot-reports.service` запускает `run.py`.
Управление и просмотр журналов через systemd:

```bash
service bot-reports status
service bot-reports restart
journalctl -u bot-reports -n 100 --no-pager
journalctl -u bot-reports -f
```

У службы `bot.service` другой проект — бот анализа тендеров. Наличие активной
службы подтверждает запуск процесса, но не доставку каждого отчёта: статус
доставки Google Sheets смотрите отдельно в отчёте админки.

## Известные риски и tech debt

- `ALLOWED_CHAT_IDS` проверяется при добавлении бота в группу, но не перед
  каждой командой. Пустой whitelist означает доступ без ограничений. Для
  security by design стоит централизовать авторизацию входящих команд.
- Синхронные вызовы `httpx`, `gspread` и SQLAlchemy выполняются внутри async
  handlers. При росте нагрузки вынести blocking I/O в worker/thread и
  батчить обращения к Google Sheets.
- Telegram- и MAX-реализации `/h` заметно дублируют бизнес-логику. При
  следующем функциональном изменении сначала оценить выделение общих helpers,
  чтобы платформы не разошлись по поведению.
- MAX загружает вложение по URL из payload события. Для защиты от SSRF стоит
  проверить allowlist доменов MAX, запрет приватных адресов и redirect policy.
- Доставка `/b` и `/h` в Sheets использует очередь и повторы, но не является одной
  распределённой транзакцией. Контролируйте `sheets_status` в админке и журнал
  worker. При ошибках нужно проверять статус доставки обоих типов отчётов.
- `.env.example` пока не содержит `MAP_BOT_READ_API_KEY`, хотя код его
  поддерживает.

Не исправляйте эти пункты попутно: сначала согласуйте scope конкретной задачи.

## Обновление сценария ходок (16.10.2026)

Порядок выкладки: миграция панели `2026_10_16_000022_add_trip_pickup_reports`,
затем `map-service/api.php` вместе с `trip_pickup.php`, затем бот и
`service bot-reports restart`. Сначала применяйте изменения схемы и API:
новый бот не считает отчёт принятым, если API не подтвердил очередь.
Старые строки кассы не импортируются в новые отчёты автоматически.
